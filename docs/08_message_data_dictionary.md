## 0. 总览

同一辆车、同一组属性（车架号 / 车型 / 颜色 / 平台 / 黑顶 / 返工）存在**两条独立记录渠道**：

| 链路 | 报文 | 载体 | 视角 | 长度 |
|---|---|---|---|---|
| 车间 PLC 实时链路 | 30 字符 BodyID 报文 | `ods.rb_position_data.raw_data` | 实时快照（车走到哪报到哪，车走清空） | 30 字符定长 |
| MES 过站链路 | MDS_DATA 电报 | `ods.carbody_history."MDS_DATA"` | 过站历史（每过一站一封，永久累计） | 237 字符定长 |

两条链路的同类字段可跨源互证（见 §1.3、§2.2），但**位序排列不同**（预留字段位置不同），跨源映射时勿按顺序硬套。

## 1. 30 字符实时报文（滚床 PLC 报文）

### 1.1 原始定义（文档/源码依据）

| 项目 | 内容 |
|---|---|
| 来源 | 车间 PLC 通过 WebSocket 实时上报（Tag 后缀 `.M1003_BodyID`），由 data_saver_service 落库 |
| 载体 | `ods.rb_position_data.raw_data`（及源库同名表 `rb_position_data`） |
| 长度 | 30 字符定长；无车时为空占位报（30 个 `-`） |
| 文档出处 | `docs/记录型数据库方案/需求.md`（原始需求第 13-20 行）、`docs/websocket_subscription_analysis.md`（位定义表第 73-80 行）、`docs/数据库设计最佳实践指南.md`（字段注释） |
| 解析实现 | `rb_position_manager_postgresql.py` → `VehicleDataParser.parse()`（Python 切片，0 起始） |

**位定义（0 起始索引）**：

| 0 起始 | 1 起始 | 字段 | 原始定义原文 |
|---|---|---|---|
| 0-13 | 1-14 | vehicle_id | 车身 ID（14 字符，产品车以 78202 开头） |
| 14-18 | 15-19 | body_type | 车身代码（5 字符） |
| 19-22 | 20-23 | color_code | 颜色代码（4 字符） |
| 23-25 | 24-26 | platform_code | 车型平台（3 字符，如 MLB/MQB） |
| 26 | 27 | black_roof_flag | 是否黑色车顶标志位 |
| 27 | 28 | rework_flag | 是否返工车标志位 |
| 28 | 29 | reserved_1 | 预留 |
| 29 | 30 | reserved_2 | 预留 |

**实测样本**（2026-09-24 快照）：

```text
78202663907011 XV32Q 1FA1 ADP 1 2 1 -     ← 黑顶车(1)、返工=2、预留1=1
78202683920144 2N54Y 2T2T MQB 0 0 0 -     ← 单色车
78202664101876 YM33J 7171 ADP 0 0 0 6     ← 预留2 出现 "6"
```

### 1.2 字段赋值说明（rework_flag 原文）

引自 `docs/数据库设计最佳实践指南.md` 与 `docs/记录型数据库方案/1_最终数据库设计方案_mysql版本.md`：

- `black_roof_flag`（第 26 位）：`1` 表示有黑色车顶，`0` 表示无黑色车顶；
- `rework_flag`（第 27 位）：`0` = 正常车辆（一次喷涂），`1` = 返工车，`2` = 黑顶的第二次喷涂。

### 1.3 数据验证结论（2026-09 实测）

1. **长度恒定**：快照中所有非空报文 = 30 字符，无例外。
2. **各标志位实测值域**（快照口径，非全量历史）：

| 位 | 实测值域 | 验证/推断 |
|---|---|---|
| 26（黑顶） | {0, 1, -} | 与 MDS 137 跨源比对 804/804 一致 |
| 27（返工） | {0, 1, 2, -} | 与 MDS 139 对应（802/804 一致，2 条为时点差），含「黑顶二次喷涂=2」 |
| 28（预留1） | {0, 1, -} | 实测跟随 26 位变化（0/0、1/1 成对）——与 MDS 137/138 的镜像现象一致，疑非纯预留 |
| 29（预留2） | {-, 0, 2, 3, 6} | 出现 2/6/3，官方语义未知；样本集中在 `L3F06 4.5米打磨前储存线`、`L3F30 黑车顶F30烘房`、`L3F02 一线预处理储存线`，车辆号段多为 782026839xxxxx / 7820266410xxxx |

3. **与 MDS_DATA 的位对应关系**（跨源验证结论）：

| 滚床索引（0 起始） | MDS 位置（1 起始） | 字段 | 验证强度 |
|---|---|---|---|
| 0-13 | 31-44 | vehicle_id | 全量比对 6,623,848/6,623,849 |
| 14-18 | 45-49 | body_type | 100% |
| 19-22 | 59-62 | color_code | 987 对共样 0 不一致 |
| 23-25 | 51-53 | platform_code | 位序对应（未单独全量验证） |
| 26 | 137 | black_roof_flag | 804/804 |
| 27 | 139 | rework_flag | 802/804 |
| 28 | 138 | reserved_1 | 推断对应（未单独验证） |
| 29 | 140 | reserved_2 | 推断对应（未单独验证，两侧值域差异见 §2.3） |

4. **平台代码第三位规律**（实测）：`B` = MQB/MLB/MEB 系列，`P` = ADP。
5. **⚠ SQL 校验操作陷阱**：本表位号是 **0 起始**（Python 切片直接用）；PostgreSQL `substring()` 是 **1 起始**，写 SQL 时必须 **+1**（黑顶位应写 `substring(raw_data, 27, 1)`），否则会取到平台代码最后一位（B/P）。

## 2. MDS_DATA（MES 过站电报）

### 2.1 原始定义（文档/源码依据）

| 项目 | 内容 |
|---|---|
| 来源 | MES 在各过站读写站（`RW_STATION_ID`）下发的电报；源头 SQL Server `carbody_history`，经 `refresh_carbody_ods.py` 同步至 `ods.carbody_history` |
| 长度 | 定长 237 字符 |
| 电报类型 | TS / TC / TE / TB / TO / TI 六种（长度一致） |
| 文档出处 | `carbody_etl/carbody_history/MDS数据提取规则.md`（8 字段规则）、`docs/00_analytics_db_architecture.md`（提取实现） |
| 提取实现 | `meta.refresh_carbody_dim()` → `substring("MDS_DATA", 位置, 长度)`；门槛条件 `length >= 140` |

**提取的 8 个字段（1 起始位置）**：

| 位置 | 字段 | ↔ 滚床索引（0 起始） |
|---|---|---|
| 31-44 | vehicle_id | 0-13 |
| 45-49 | body_type | 14-18 |
| 51-53 | platform_code | 23-25 |
| 59-62 | color_code | 19-22 |
| 137 | black_roof_flag | 26 |
| 138 | reserved_1 | 28 |
| 139 | rework_flag | 27 |
| 140 | reserved_2 | 29 |

**示例片段**：`...1FBU0---1FBU0---0010--------...`（137-140 = `0010`，是 `-` 分隔的独立 4 位块）

**消费链路**：`ods.carbody_history` → `dim.carbody_registry`（一车一行）→ `dim.dim_vehicle_profile` → `fct.* / mart.*` 物化视图。

### 2.2 数据验证结论（2026-09 全量实测）

1. **定长 237 无例外**（6 类电报 min=max=237）→ 按位置硬编码截取安全；若 MES 改版，长度偏离 237 是第一个预警信号。
2. **位序正确性三重验证**：
   - 31-44 位 `vehicle_id` 与独立列 `BODY_ID` 比对 6,623,848/6,623,849 一致（唯一孤例 `78114319203…` ID=114319203）；
   - 45-49 位 `body_type` 与 `BODY_TYPE` 左 5 位 100% 一致；
   - 137/139 位与滚床报文 26/27 位跨链路比对全部通过。
3. **137-140 完整值域穷举**（含业务有效值与异常值）：

| 位 | 完整值域 | 关键说明 |
|---|---|---|
| 137 | {0, 1, -} | 黑顶标志；与颜色代码 `A1` 后缀 100% 互证（58 万黑顶车零反例） |
| 138 | {0, 1, **2**, -} | 文档写「预留」但实测**跟随 137**；值 2 仅 13 条（1 辆车）——疑非纯预留 |
| 139 | {0, 1, 2, **3**, -} | 0=正常 / 1=返工 / 2=黑顶二次喷涂；**3 仅 4 条**（2026-04-17 凌晨异常报文） |
| 140 | {0, **1**, -} | 文档写「预留」但值 1 有 169,760 条，**与黑顶车强相关**（137-140 组合以黑顶车 `1101`/`1121` 为主，另有单色车 `0001`）——官方语义未明 |

4. **语义推断（重点结论）**：
   - **137/138 基本终身不变**：137 位真实变化仅 4 辆车、138 位仅 6 辆（其余「变化」为空占位符重置或调试号 `99999999999999` 造成）；发生变化的车辆全部与「返修补喷黑顶」相关；
   - **「非 A1 色但 137=1」的 123 条例外** = 4 辆返修补喷黑顶车（F7F7 / V9V9 / I1I1 / 2R2R 各 1 辆，2026-08 下旬批次，139=2）；
   - **139=2 的触发高度集中**：`14IS260`（47%）+ `24IS185`（26%）= 73%，前 9 个读写站 = 98.4%；
   - **138 不是 137 的简单影子**：有 2 辆车「137 不动、138 单独变化」；
   - **140=1 疑似与黑顶流程相关**（黑顶车 1101/1121 组合为主）——待官方定义确认。
5. **注意 MDS 四位排列顺序与滚床不同**：MDS 为「黑顶 137 → 预留1 138 → 返工 139 → 预留2 140」（预留夹中间），滚床为「黑顶 26 → 返工 27 → 预留1 28 → 预留2 29」。

### 2.3 待核实清单

| # | 待核实项 | 说明 |
|---|---|---|
| 1 | **138 的官方定义**（是预留还是黑顶衍生？取值 2 的含义） | 现有文档写「预留」，但数据行为不吻合 |
| 2 | **139=3 的官方定义** | 仅 4 条、2026-04-17 凌晨扎堆，疑系统异常 |
| 3 | **140=1 的官方定义** | 16.9 万条与黑顶/返工流程强相关 |
| 4 | **滚床 29 位（2/6/3）与 MDS 140 位（1）是否同一字段** | 两侧值域完全不同；若都对应「预留2」，需确认是否因时间口径差异（快照 vs 末次过站） |
| 5 | **MDS 其余 229 个字符的模板语义** | `TS` 头、`1FBU0` 段（出现两次）、`---` 分隔符、大段留空等 |
| 6 | **六种电报类型（TS/TC/TE/TB/TO/TI）的业务含义** | 各代表什么过站场景 |
| 7 | **颜色码完整字典**（59-62 全部组合 → 物理色名）与平台码字典（含异常小写 meb/mqb） | 数据侧可先自查值域清单 |

## 3. 实用口径速查（分析场景）

| 分析问题 | 推荐口径 |
|---|---|
| 判断订单黑顶车（出厂配置） | 颜色代码后 2 位 = `A1`（如 `0QA1`）；滚床 19-22 位 / MDS 59-62 位 |
| 判断当前黑顶状态 | 137 位（MDS）/ 26 位（滚床） |
| 判断返工 | 139 位（MDS）/ 27 位（滚床）：0=正常、1=返工、2=黑顶二次喷涂 |
| 过滤空占位报文 | MDS：`length("MDS_DATA") >= 140` 且车辆 ID 非 `--------------`；滚床：`raw_data <> '------------------------------'` |
| 值域校验硬约束 | MDS 139 位勿写成「仅允许 0/1/2」——存在 4 条异常值 3 |
| 实时位置 vs 历史档案 | 实时位置走 `ods.rb_position_data`；一车一档走 `dim.carbody_registry` |
