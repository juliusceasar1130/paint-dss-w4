## 2. 性能踩坑与定版（2026-09-24）

**现象**：bootstrap 初版按 ID 序走 consume 同款 skew 分流 → 真库 120h 干跑 15min 超时。

**诊断**（只读窗口函数实测）：120h 窗内 **ID 序 ts 逆序率 52.18%**（137,448 / 263,425），
其中 51.65% 落在 15min skew 窗内 → 每条触发一次 per-car 事件日志子查询 ≈ 13.6 万次
DB 往返。纯 SQL 拉取 26 万行仅 1.3s——瓶颈 100% 在 skew 子查询。

**定版**：bootstrap 喂入序 = **(BODY_ID, ts, ID) 升序纯 `pool.ingest`**——
状态机逐车独立、车内 ts 序即正确序；回放窗是完整数据、无「迟到」概念（skew 分流是
增量流专属）。26 万行 3.7s（≈ 7 万行/秒）。「同一个 ingest」契约不变（单一状态机，
`monkeypatch` 计数 50,000/50,000 钉死）。
**残留（T2.6 关注）**：replay_cursor 主循环走 consume 同款 skew 分流，KW37 七天回放
预计 30–60min（每车每轮一次重算、幂等），一次性干跑可接受；若需提速再优化（按车合并

## 8. 发现与修复（T2.6 干跑暴露）

### F-1 consume 水位跳过丢行（系统性，真库实证）

**① 丢行定理与量化**：consume = `WHERE "ID" > wm AND "DATE_EVT" <= now ORDER BY "ID"` +
wm = max(已拉 ID)。凡存在 ID 更大而 ts 更小的行 Q，Q 先被拉、wm 跳越，R 永久丢失。
真库 KW37 day1（288 轮回放模拟）：**221 / 59,152 = 0.37% 行永久丢失**（pending 0 = 非延迟）。

**② 干跑性能连带发现**：首轮 7.8min 前曾卡 11h+——每轮按 ID 序 dispatch 时，52% 的
ID/ts 逆序行把刚到期行误判入窗内迟到 → 每车 per-car 子查询（≈ 20 万次）。修复：
**consume 拉取后先按 (ts, ID) 排序再 dispatch**（front 单调前进，全部走行序 ingest；
真迟到语义不变，`test_consume_normal_and_late_split` 复验）。7.8min 完成。

**③ 真库 wm 中毒实案（09-13）**：一条 ID 极大、ts 极早的乱序 ETL 行在 09-13 ~07:00 把 wm
跳到后续几乎所有行 ID 之上 → 09-13 07:00–17:40 约 11h 数据丢失（仅 17:40 一行 ID 更大幸存
→ RECOVERY）。**B3 护栏正确报出 203 轮 STALE**——护栏对丢行/断流的敏感性获实证。

**④ 修复（已实现，TDD）**：**周期 120h 全量重建**——`VehiclePool.reset()` +
`bootstrap`（同一状态机，3.7s）每 `DSS_REBUILD_HOURS`（默认 24h）一次，主循环
（wall_clock 与 replay_cursor 均生效）；回放结束后在终点再重建一次（回放终态 = 纯
bootstrap 真值，验收锚点）。水位对齐只升不降（F8）。丢行/中毒影响上限 = 一个重建间隔。
修复后 GT 核对 1.15% → **0.11%**（残差 1 台 = 空撬假号）。替代方案（双游标 ts 水位 /
gap-aware wm / 接受 0.37%）对比见 §10 待拍板①。

### F-2 dim cross_check 在历史时点结构性无效

`dim.dim_vehicle_profile` 是**现态快照**（carbody_last_seen_at = 该车全史最后事件）：
回放至历史时点时参考集 = 「至今仍卡在中线的车」≠ 该时点应有的在制集 → 末态 dim 核对
99.79% 差 941 台是口径假象，非池错误。**定版口径**：回放验收门 = **GT SQL 真值核对**
（独立于池：120h 窗内有事件且末事件站 ∉ 9 站的对称差，纯 GROUP BY 无窗口函数——
全表窗口函数曾致 Postgres 崩溃，2026-09-25 实测）；dim cross_check 仅用于当前时刻
（在线生产启动验收）。见 §10 待拍板②。
