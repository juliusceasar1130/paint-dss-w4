## 一、审核结论

**【归因完全属实 / 强烈推荐方案 (α)，但必须补齐 2 处关键边界设计】**

1. **归因结论复核**：G1 门判超差（相对差 0.833pp > 0.5pp，超差集中于 09-09_day 与 09-08_mid）的核心根因**100% 确证为 Doc14 §5 R3 规则引发的「raw 139 位出环后残留」导致的静态/滚动不对称**。在 29 辆全量差异样本中，出环后位残留且落入总装工位导致 51.28h 虚高漏计的高达 **25 辆（占漏计总量的 92.6%）**；真库全窗统计证实，95.92%（988/1,030 辆）的返工车在物理出环后其 MES MDS 数据 139 位**终生不清除**。
2. **方案 (α) 定性**：方案 (α)（将离线净化出环窗镜像回在线状态机）是消除静态/滚动不对称的**唯一物理正确解**。方案 (β)（拖延至 M5）、(γ)（消费层兜底乱切）、(δ)（给总装站假造环内表）均属治标不治本或违背物理语义，坚决不予采纳。
3. **重大审核纠偏（必须吸纳入方案 α）**：
   - **纠偏 1（边界 b 黑顶穿透暗雷）**：brief 原判断认为“黑顶 '2' 已被 oven 三防 + 白名单覆盖，不需要出环守卫”。**此判断存在致命逻辑盲区**！`resolve_effective_flag` 中的白名单拦截仅在 `not passed_oven` 时生效；黑顶车出环到达 33IS450 时已出炉（`passed_oven=True`），白名单直接被穿透，若位残留依然会返回 '2'！真库证实 45.02%（447 辆）黑顶车在出环后 raw 139='2' 残留。**方案 (α) 的出环守卫必须升级为统一拦截 '1' 与 '2'**。
   - **纠偏 2（单车 CLI 联动遗漏）**：`spike_w3/dashboard.py` 的 `_compute_eta_unified` 直接基于 DB 历史推断状态，必须同步增加针对 25IS 出环事件的查询，否则单车看板在总装工位仍会误判为环内返修车。

### 审核点 2：R3' 修复方案 (α) 设计审查（含边界 a 至 e）

#### 1. 核心设计评价
- 在 `VehicleState` 增加状态标记，在 `_ingest_core` 中监听 `{25IS010, 25IS110, 25IS210}` 出口站置 True，在 `resolve_effective_flag` 中增加可选参数过滤：
  - **正确性**：逻辑直击痛点，在线状态机真正具备了“感知物理出环”的能力；
  - **最小性**：仅在 `VehicleState` 增加 1 个布尔位，纯增量修改，不影响旧数据库表结构；
  - **无状态漂移**：在 periodic rebuild 与 bootstrap 重建时，事件流重放天然按时间序走 `_ingest_core`，重建后状态与实时推进状态具有完全确定性的数学一致性。

#### 2. 边界 a 至 e 逐条深度评判

- **边界 a（返修再入环，二次返修）**：
  - *设计*：出环（True）后再遇 raw-1 置 False（重新起窗）。
  - *审核结论*：**完全合理，物理自洽**。真库 SQL 实测排查证实：在 KW36/37 整个回放窗内，在经过 25IS 出口后**再次物理进入返修站（15IS065/13IS065/14IS065）的车辆数为 0**！现实生产中出环后极罕见再次大返工。方案逻辑设计严谨，且与离线单窗假设在实测上零冲突。
- **边界 b（黑顶 '2' 是否需要同样的出环守卫？）——【重大发现与纠偏】**：
  - *brief 原设计*：“R2 已有 oven 三防 + 白名单，出环后 33 系站不在白名单会被阻断为 '0'，不加出环守卫”。
  - *审核纠偏*：**此假设被代码执行与真库数据证伪，属于设计漏洞！**
    1. 代码逻辑验证：`eta_v2.py::resolve_effective_flag` line 226 中的白名单判断被 **`if not passed_oven`** 保护。对于流经 25IS 到达 33IS450 的黑顶车，**`passed_oven` 恒为 True**！白名单拦截被彻底绕过，直接在 line 228 返回 **`'2'`**（测试脚本直接调用证实该行为）；
    2. 真库数据验证：全窗经过 25IS 的 993 辆黑顶车中，**447 辆（45.02%）出环后仍带 raw 139='2'**！
    3. 隐患：一旦某班次在锚点时刻有黑顶车处于 33IS450/487，系统同样会因 `loop_rem` 缺行落入 `dim_loop_duration(flag='2')`（14h~18h）而引发同类漏计！
    4. *落地纠偏指令*：出环守卫必须统一化。建议字段命名为 `loop_exited: bool = False`（或在过 25IS 时统一将返工与黑顶出环标记置 True），**在 R2 逻辑末尾同样增加：`if loop_exited: return '0'`**。
- **边界 c（出环站集合定义）**：
  - *审核结论*：**坚决支持使用 `{25IS010, 25IS110, 25IS210}` 三站**。这三站是涂装三大工艺线通往注蜡与总装的唯三物理交接出口。离线 `sqlbase.py` 净化窗亦采用这三站作为 `t_rw_end`/`t_bt_end`，两端对齐最为纯正。
- **边界 d（池残留 2 辆水印逆序）**：
  - *审核结论*：**赞同不在此步修改**。属于底层事件流 ingestion 机制的固有乱序容差（~52% 乱序率下每日约 1~2 辆），改动涉及水印核心调度，属于 P3 架构演进，不应与状态机修复耦合。
- **边界 e（若修复后 G2 回升超线，关账口径）**：
  - *审核结论*：修复 R3 后，消除漏计会使滚动预测值（489）向实际值（578）靠拢，中位绝对误差预期平稳甚至改善；若仍维持在 10.6%~11.0% 区间，维持 (a) 路径“留痕为离线基线 + 转 W3 在线 M5 验收”完全合理。

### 审核点 3：影响面与调用链排查

审核团队全库排查了消费链条：

1. **`spike_w3/predictor.py::rem_of`**：核心消费点，透传 `v.loop_exit_since_raw1`，行为预期完全一致。
2. **`spike_w3/dashboard.py::_compute_eta_unified`【遗漏点补齐】**：
   - 现行单车 CLI 查询直接查询 DB 历史派生 `passed_oven`，但不经过池缓存；
   - 必须在 `_compute_eta_unified` 中同步补充 1 条轻量查询，派生该车是否已过 25IS 出口：
     ```python
     cur.execute('SELECT COUNT(*) FROM ods.carbody_history '
                 'WHERE "BODY_ID" = %s AND "DATE_EVT" <= %s '
                 "AND \"RW_STATION_ID\" IN ('25IS010', '25IS110', '25IS210')",
                 (body_id, as_of))
     loop_exited = cur.fetchone()[0] > 0
     ```
     并将 `loop_exited` 传给 `resolve_effective_flag`。否则，单车看板在查询出环后车辆时仍会显示 `eta_kind: in-loop` 并报返修延误，造成看板与在线预测分裂。

   - 启动检查不校验单个车辆内部标志位，零破坏。

   - **对策认同**：严格执行 2026-09-25 拍板口径——**生产默认 `DSS_ALPHA_MODE=off`**，中班自适应调优留待后续就餐工时日历专项攻坚。
2. **09-12_mid 尾带 +77 台现象**：
   - 查验数据证实，09-12_mid 实际产量高达 573 台（名义预测 552 台，5h 误差仅 3.14%）；
   - 该班次在 04:15~04:45 班末尾段确实有大量车辆集中下线，属于真实物理排产，非模型虚标；
   - 维持现状，不引入人工截断，口径受控。
