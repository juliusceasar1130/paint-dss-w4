### 建议项 1：明确 `SQL_LOOP_DURATION` 学习计算中提取 `exit_t` 须 JOIN `tmp_ev_base`

- **位置**：`docs/15` §W4.2a（第 206 行）、§0.4 表契约（第 173 行）
- **问题说明**：  
  文档指出：“`dim_loop_duration` 扩列……SQL 改从 `tmp_loop_bounds` 逐车 L（end NULL → exit_t 回退，D4）”。  
  但查阅 `spike_w1/sqlbase.py` 中 `tmp_loop_bounds` 的 DDL 与 SELECT 定义（L79-80），其仅包含 6 列：  
  `(body, bt, t_rw_start, t_rw_end, t_bt_start, t_bt_end)`，**表中并不包含 `exit_t` 列**。  
  若实现时开发人员直接从 `tmp_loop_bounds` 取 `exit_t`，将触发 `column "exit_t" does not exist` 错误。
- **技术建议**：  
  在 W4.2a 实现说明中补充声明：  
  `SQL_LOOP_DURATION` 应通过 `tmp_loop_bounds b JOIN (SELECT body, max(exit_t) AS exit_t FROM tmp_ev_base GROUP BY body) e USING (body)` 来获取无网关车的 `exit_t`。  
  此举同时具备关键业务收益：由于 `tmp_ev_base` 内连接了 `entry` 与 `exit_stn`，该 JOIN 会**自然过滤掉全史 254 辆（学习窗 88 辆）在制车（无 exit_t）**，确保学习器仅消费具备完整行程的闭环车与 6 辆旁路车，完美对齐 D4(a) 拍板口径。

### 建议项 2：澄清 `02_replay_shift.py` 中 `direct_nocomp` 在新推断引擎下的对照语义

- **位置**：`docs/15` §W4.3d（第 219 行）、`spike_w2/02_replay_shift.py`（L298–313）
- **问题说明**：  
  现行 `02_replay_shift.py` 中：
  ```python
  eta_d, used = eta_v2.estimate_event(t_e, st_e, fl_e, model, week, tables, comp_excl)
  eta_d0, _ = eta_v2.estimate_event(t_e, st_e, fl_e, model, week, tables, frozenset())
  ```
  `eta_d0` 是通过传入空集 `frozenset()` 关闭 ⑥b 豁免，用于统计 `cnt["direct_nocomp"]`（量化补偿净化的班次级净效果）。  
  但在 W4 双环统一推断引擎 `estimate_event_unified` 中，由 `expected_delay` 表直接替代了旧的 $p \times L_1 + p \times L_2$ 与 `comp_excl` 豁免机制（见 `docs/15` L176、L216 及 `docs/10` §4）。在统一引擎内部，`comp_excl` 已不参与计算。  
  若 W4.3d 切换为 `estimate_event_unified` 时仍机械传入 `comp_excl` 与 `frozenset()`，两者输出将完全一致（`eta_d == eta_d0`），导致报告中的 `direct_nocomp_err_pct` 与 `direct_err_pct` 恒等，失去对照意义。
- **技术建议**：  
  在 W4.3d 中对 `cnt["direct_nocomp"]` 的行为做显式规定，推荐两种方案之一：  
  1. **（推荐）定义为“无延误基线对照”**：计算 `eta_d0` 时传入空的延误字典或令 `delay = 0`，用以量化 `expected_delay` 的整体加入对班次产量的净纠偏效果；  
  2. **（备选）保留旧引擎基线**：`eta_d` 走 `estimate_event_unified`，而 `eta_d0` 维持调用旧 `estimate_event`（旧路径），直接对拍新旧引擎的宏观班次达成差异。

### 建议项 3：防范 `resolve_hierarchical` 对 `expected_delay` 的反向列序与双人群门槛穿透

- **位置**：`docs/15` §0.2（第 144–147 行）、W4.3a（第 216 行）
- **问题说明**：  
  `tables` 中各维表的列序存在结构性反差：  
  - `rem` / `loop_rem` / `loop_dur`：第 0 位为 P50，第 1 位为 Mean，门槛为单一 `row[-1] >= 30`；  
  - `expected_delay`：格式为 `(delay_mean_s, delay_p50_s, n_fut, n_clean)`，第 0 位为 Mean，第 1 位为 P50，且要求 `n_fut >= 30 and n_clean >= 30` 双人群达标。  
  若通用层级回退函数 `resolve_hierarchical` 统一按 `row[0]` 或统一检查 `row[-1]`，会直接导致：① `mode='vehicle'` 与 `mode='shift'` 取值相反（Mean/P50 颠倒）；② 忽视 `n_fut` 样本量不足导致的降级。
- **技术建议**：  
  在 `spike_w2/eta_v2.py` 实现时，强烈建议将 `expected_delay` 的查询独立封装为专用的 `resolve_expected_delay(tables['expected_delay'], station, model, mode)` 函数，显式索引：  
  - `mode == 'shift'` $\rightarrow$ 取 `row[0]`（`delay_mean_s`）；  
  - `mode == 'vehicle'` $\rightarrow$ 取 `row[1]`（`delay_p50_s`）；  
  - 有效性条件严格钉死为 `row[2] >= 30 and row[3] >= 30`，避免通用回退函数的隐式约定带来混淆。

## D. 对拍板项的意见（63 辆无烘房出口车处理建议）

- **待拍板事项**：  
  全史存在 260 辆行程完整（具备 entry 与 exit）但从未记录过三座烘房出口站的车辆（占全史 0.28%），其中 63 辆携带有效的 `137=1 ∧ 139=2` 标记。现行逻辑按 Doc14 §4 统一 SQL 的**严格语义**执行（因 `first_oven` 为 NULL，`t >= o.t_oven_out` 判定失效，无黑顶锚点，黑顶标记被抑制为 '0'）。备选方案为“退化为首次有效打标”。
- **实测深入分析**：  
  抽样分析该 63 辆车轨迹发现，大量车辆的 `137=1 ∧ 139=2` 首次打标位置直接出现在出口工位（如 `K3IS140`），其本身可能属于线下补录、返修下线再入等非标准涂装流动车。
- **技术评估与影响分析**：  
  1. **物理逻辑自洽**：烘房高温交联固化法则规定“出炉前（未烘干冷却）的 139=2 均为假信号”。若车身从未过面漆烘房，物理上不存在黑顶二喷的二次进环工艺。  
  2. **离在线状态机一致性（核心红线）**：  
     在线端 `stream_pipeline.py` 中，车辆状态 `v.passed_oven` 必须经由 `OVEN_OUT_STATIONS` 站触发置为 `True`（规则 O1）。若一辆车未过烘房出口，在在线推断时其 `v.passed_oven` 恒为 `False`，在线状态机 `resolve_effective_flag` 的规则 2.2 / 2.3 会坚决将其抑制为 `'0'`。  
     如果离线学习 SQL“退化”将其作为黑顶环学习，将导致**离线标记为 '2'、在线识别为 '0' 的离在线分裂**！  
  3. **样本量级极微**：63 辆车仅占全史 5,813 辆黑顶锚点车的 1.08%（在 04-14 $\to$ 08-15 学习窗内仅个位数），且其行程分布与正常主线完全相融，被抑制为 '0' 对剩余时间分布学习无副作用。
- **明确决策建议**：  
  **强烈建议维持现行“严格语义”（不退化）**。严守物理不可逾越门槛，保持离线数据打标与在线状态机判定规则的高度同构与自洽。
