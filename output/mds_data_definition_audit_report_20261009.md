## 3. 报文长度差异与数学映射模型

PG 库中 `ods.carbody_history."MDS_DATA"` 全量 7,093,971 行记录均为**恒定 237 字符**。官方定义为 **200 字节**。

### 3.1 长度分解公式

$$237\text{ (PG 字符)} = \underbrace{30}_{\text{Header}} + \underbrace{124}_{\text{Byte 0..123}} + \underbrace{18}_{\text{Byte 124..135 (DINT文本展开)}} + \underbrace{65}_{\text{Byte 136..199（64字节，SkidDest 4字节→5位文本，净+1位）}}$$

```text
+---------------------------------------------------------------------------------------------------+
|                                     PG MDS_DATA (定长 237 字符)                                     |
+-------------------+----------------------------+-----------------------+--------------------------+
|  MES 通信头 (30)  |    Payload 前半段 (124)    |   时间展开段 (18)     |   Payload 后半段 (65)    |
|   PG 1 .. 30      |        PG 31 .. 154        |     PG 155 .. 172     |      PG 173 .. 237       |
+-------------------+----------------------------+-----------------------+--------------------------+
|  TS00000000...--  | 782026816...               | -9260414010650----    | 20260414164435...        |
+-------------------+----------------------------+-----------------------+--------------------------+
                    | 对应官方 Byte 0 .. 123     | 对应官方 Byte 124..135| 对应官方 Byte 136..199
                    | [偏移量 = +30 (1-based +31)] | [12字节 DINT 展开为18] | [偏移量 = +36 (1-based +37)]
```

### 3.2 两大偏移变化点

1. **头部协议封装（偏移 +30）**：
   - PG 1..30 是 MES 系统的电报通信头（如 `TS00000000  ------0000000000--`、`TC00000000LD0000--0000000000--`），包含电报类型（TS/TC/TE/TB/TO/TI）与工位读写类型。
   - 官方定义的 Byte 0（`BodyId`）落入 PG 的 **第 31 位**（1-based）。
2. **中段时间数值展开（膨胀 +6 字符）**：
   - 官方 Byte 124..135 定义为 3 个 `DINT`（4 字节无符号整数，共 12 字节）：`ArrivalDate` (4) + `ArrivalTime` (4) + `CarrierID` (4)。
   - MES 电报在传输序列化为 ASCII 字符串时，将其展开为 18 字符文本：
     `[前导符 2位]` + `[YYMMDD 6位日期]` + `[HHMMSS 6位时间]` + `[CarrierID 4位]` = **18 字符**。
   - 这比二进制的 12 字节多出 6 字符，导致 **官方 Byte 136 开始的后半段字段，在 PG 中的相对偏移量由 +30 变为 +36（1-based 偏移 +37）**。
3. **后半段字符展开（+1 字符）**：后半段 Byte 136..199（64 字节）在文本电报中对应 **65 字符**——其中 4 字节 DINT `SkidDestination` 序列化为**5 位十进制文本**（实测 `00380`/`03180` 有前导零、`17001` 超 4 位），其余后半段 DINT 均保持 4 位。此 +1 即 237 长度分解中 64 字节→65 字符的唯一差异；**PG 237 是 `Reserve2` 的第 18 个字符，无独立尾部占位符**（全量判据：209..213 无 4dash+数字 / 4数字+dash 混合模式、`FULLSKID` 起于 220、213 位值域含 3/6/7/8/9）。

### 5.1 疑点 1 & 3：138 与 140 为什么不是纯预留？
- **原文档疑点**：138 跟随 137 变化且有 13 条取值 2；140 有 172,154 条取值 1，高度关联黑顶车，官方语义未知。
- **官方审查结论**：
  - **PG 138 (Byte 107) 官方名称为 `CodeA`**，不是预留位（值域 {0,1,2,-}，取值 2 仅 1 辆车）！
  - **PG 140 (Byte 109) 官方名称为 `KVS Flag`**！实测 KVS=1 全量为 172,154 行（约 75% 黑顶、25% 单色，与双色车顶不等价）。具体业务下发条件与配置系统全称待用户确认（见 §7）。

### 5.2 疑点 5：为什么会出现两段 `1FBU0---` 颜色代码？
- **原文档疑点**：示例片段中 `...1FBU0---1FBU0---...` 出现两次，大段留空与分隔符语义未知。
- **官方审查结论**：
  - PG 121..128 (Byte 90..97) 为 **`APT_ColorCode1`**（自动化主色）；
  - PG 129..136 (Byte 98..105) 为 **`APT_ColorCode2`**（自动化顶色）。
  - 单色车两段相同；双色车（黑顶车）实测为 `2LPU0---` 与 `A1PQ0---`，完全印证双色喷涂的物理色码定义。

### 5.3 生产代码影响评估
审查了 [`dim.dim_vehicle_profile`](file:///F:/000_dev/Python/workplace/paint-dss-w4/docs/00_analytics_db_architecture.md) 与刷新存储过程 [`meta.refresh_carbody_dim()`](file:///F:/000_dev/Python/workplace/paint-dss-w4/docs/00_analytics_db_architecture.md)：
- 当前 SQL 切片：
  - `substring("MDS_DATA", 45, 5)` 取车型
  - `substring("MDS_DATA", 51, 3)` 取平台
  - `substring("MDS_DATA", 59, 4)` 取颜色
  - `substring("MDS_DATA", 137, 1)` 取 CodeF（用作黑顶判断）
  - `substring("MDS_DATA", 139, 1)` 取 CodeB（用作返工判断）
- **评估结论**：**生产切片物理位置全部正确，逻辑运行安全，无需紧急重构 SQL**。但后续可在维表中补充官方字段命名注释，并将 `KVS Flag`、`APT_ColorCode2`、`skidId` 等新增高价值字段纳入车辆画像。

```sql
    "BODY_ID",
    substring("MDS_DATA", 59, 4)   AS topcoat_color,     -- TopCoatColor (PG 59..62)
    substring("MDS_DATA", 121, 8)  AS apt_color_1,       -- APT_ColorCode1 (PG 121..128)
    substring("MDS_DATA", 129, 8)  AS apt_color_2,       -- APT_ColorCode2 (PG 129..136)
    substring("MDS_DATA", 137, 1)  AS code_f,            -- CodeF (PG 137)
    substring("MDS_DATA", 138, 1)  AS code_a,            -- CodeA (PG 138)
    substring("MDS_DATA", 139, 1)  AS code_b,            -- CodeB (PG 139)
    substring("MDS_DATA", 140, 1)  AS kvs_flag,          -- KVS Flag (PG 140)
    substring("MDS_DATA", 173, 14) AS evt_timestamp,     -- TIMESTAMP (PG 173..186)
    substring("MDS_DATA", 195, 2)  AS skid_type,         -- skidType (PG 195..196)
    substring("MDS_DATA", 197, 4)  AS skid_id,           -- skidId (PG 197..200)
    "SKID_ID"                      AS col_skid_id        -- 独立列对比
FROM ods.carbody_history
WHERE "MDS_DATA" IS NOT NULL AND "BODY_ID" LIKE '78%'
LIMIT 10;
```
**复核核对要点**：
1. `col_skid_id` 与 `skid_id`（PG 197..200）必须完全一致；
2. 当 `code_f = '1'`（黑顶车）时，观察 `apt_color_1` 与 `apt_color_2` 是否呈现主色与顶色（如 `2LPU0---` 与 `A1PQ0---`）不同；
3. `evt_timestamp`（PG 173..186）是否为标准的 14 位 YYYYMMDDHHMMSS 字符串。
