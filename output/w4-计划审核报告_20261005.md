### 阻断项 2：`VehicleState` 契约扩展遗漏 `flag_137` 字段，导致在线推断引擎丢失黑顶硬约束输入

- **位置**：`docs/15` §0.3 `spike_w3` 管道契约扩展（第 142-143 行）、W4.3c（第 199 行）及 W4.3d（第 200 行）
- **问题**：在 §0.3 管道契约扩展中，仅声明了 `Event +1 字段：flag_137: str` 和 `VehicleState +1 字段：passed_oven: bool = False`，遗漏了在 `VehicleState` 中持久化 `flag_137` 字段。在制车进池后，`predictor.py` 的预测循环（`predict` / `rem_of`）只接收 `v: VehicleState`。若在制车状态不存储 `flag_137`，`rem_of` 在调用 `estimate_event_unified` 时将无法提供该车的 137 信号（或只能传入缺省值 `'0'`），导致在制车在池中滚动推断时，所有黑顶车均因 `flag137 != '1'` 被在线状态机 `resolve_effective_flag` 的第一重防护直接误杀为 `'0'`，双环在线预测引擎瘫痪。
- **证据**：
  - `docs/15` §0.3：
    ```text
    Event +1 字段：
        flag_137: str        # SUBSTRING("MDS_DATA" FROM 137 FOR 1)；4 处 consume SQL 同步
    VehicleState +1 字段：
        passed_oven: bool = False
    ```
  - `spike_w3/stream_pipeline.py`（现行代码 L42-51）：`VehicleState` 仅有 `body_type, station, flag, last_event_ts, entry_ts, exits_seen, loop_count`；
  - `spike_w3/predictor.py`（现行代码 L94-97）：
    ```python
    for body_id, v in pool.snapshot().items():
        rem = rem_of(v, t, tables, comp_excl)
    ```
  - `rem_of` 仅能从 `v` 读取属性，无从得知 `flag_137`。
- **修复建议**：
  - 在 §0.3 中将 `VehicleState` 扩展明确为 2 个字段：
    1. `passed_oven: bool = False`
    2. `flag_137: str = '0'`
  - 在 W4.3c 中补齐规则：在事件入池（`ingest` / `replay_car` / 中途收养）及状态转移时，`v.flag_137` 随最新合法事件更新或继承；
  - 同步更新 W4.3c 测试用例与 `docs/03 §0` 契约快照。

### 阻断项 3：`02_replay_shift.py` 消费端切换 `estimate_event_unified` 时缺乏 `flag137` 与 `passed_oven` 来源，且存在纯净 flag 与原始 MDS 混淆击杀风险

- **位置**：`docs/15` §0.1（第 67-77 行）、§0.2（第 104-124 行）、W4.3d（第 200 行）
- **问题**：
  1. `docs/15` §0.1 规定 `tmp_ev_base` 结构不变，其中 `flag` 列为经离线 SQL 净化后的有效值（'0', '1', '2'），表中并不包含原始 `raw_flag` 及 `flag_137`；
  2. `02_replay_shift.py` 从 `tmp_ev_base` 拉取历史事件流 `(int(t), st, fl)`；
  3. W4.3d 要求将 `02_replay_shift.py` L298 处旧入口替换为 `estimate_event_unified`；
  4. 然而 `estimate_event_unified` 内部强制执行在线状态机 `resolve_effective_flag(station, flag137, flag139, passed_oven)`。回放端没有 `flag_137`，也没有维护历史轨迹的 `passed_oven` 状态；若将已净化的 `fl` 作为 `flag139` 传入且缺省传 `flag137='0', passed_oven=False`，所有纯净黑顶（`fl='2'`）将在 `resolve_effective_flag` 内部因未满足 `flag137 == '1'` 被重置为 `'0'`；
  5. 若黑顶被全部误判为 '0'，`02_replay_shift.py` 将无法反映真实双环重构收益，导致 G2 门判（≤10% 刚性门）与车型评估完全失真。
- **证据**：
  - `spike_w2/02_replay_shift.py` L176-180：`SELECT body, station, EXTRACT(EPOCH FROM t)::BIGINT, flag FROM tmp_ev_base WHERE flag IN ('0','1','2')`；
  - `docs/15` §0.2：
    ```python
    def estimate_event_unified(t, station, flag137, flag139, model, week, tables,
                               mode='vehicle', passed_oven=False, comp_excl=frozenset()):
        eff = resolve_effective_flag(station, flag137, flag139, passed_oven)
        ...
    ```
  - `docs/15` W4.1c 宣称消费端对 `tmp_ev_base` “零改动”，但 W4.3d 却要求直接调用新引擎，离线纯净流与在线原始流契约未对齐。
- **修复建议**：在 `estimate_event_unified` 中显式支持消费端已净化 flag 输入，或定义独立重载/参数：
  - **推荐接口设计**：在 `estimate_event_unified` 中增加可选参数 `effective_flag: Optional[str] = None`（或当 `flag137 is None` 且 `flag139` 传入净化 flag 时，直接 `eff = flag139`，跳过 `resolve_effective_flag`）；
  - 在 `02_replay_shift.py` 中，调用时明确传入 `effective_flag=fl_e`（或对应参数），确保离线回放直接消费纯净打标结果，不受在线状态机缺失字段干扰；在线端（`predictor.py`）则正常传入 `(flag137, flag139, passed_oven)` 走完整状态机解析。

## B. 建议项（推荐优化）

1. **建议项 1：修正 `loop_dur` 字典行形状元组大小的表述笔误**
   - **位置**：`docs/15` §0.2 行形状扩展（第 131 行）
   - **说明**：文档中写 `loop_dur: {(flag, model): (l, l_mean, l_p90, n)} # 3 → 5 元组（C11）`。现有代码中 `tables["loop_dur"]` 的 value 是 `(l, n)`（2 元组），扩列后 value 为 `(l, l_mean, l_p90, n)`（4 元组）。建议将“3 → 5 元组”更正为“2 → 4 元组”，避免开发人员在编写 loader 或解包时产生误解。
2. **建议项 2：明确 `expected_delay` 在 `tables` 字典中的元组索引与双门槛判定规范**
   - **位置**：`docs/15` §0.2（第 120-123 行、第 132 行）
   - **说明**：`expected_delay` 的字段顺序为 `(delay_mean_s, delay_p50_s, n_fut, n_clean)`，其第 0 位为 mean、第 1 位为 p50；而 `rem` / `loop_rem` / `loop_dur` 的第 0 位均为 p50、第 1 位为 mean。建议在 `resolve_hierarchical` 的伪代码中显式注明：对 `expected_delay` 需按反向索引提取统计量，且回退判定须严格检查 `n_fut >= 30 and n_clean >= 30`（双人群各自达标），防止通用层级回退函数因统一取 `row[0]` 导致 mean/p50 颠倒。
3. **建议项 3：澄清 `01_learn_takt.py` 中自检 S2b 的演进关系**
   - **位置**：`docs/15` W4.2d（第 190 行）
   - **说明**：现行 `01_learn_takt.py` 已存在 `S2b`（首条 flag=2 集中于 `BLACKTOP_CLUSTER = ('14IS260', '24IS185')` ≥60%）。重构后 `14IS260` 假黑顶被净化为 '0'，旧 S2b 将必然失败。建议在文档中明示：将原有 S2b 替换/升级为“黑顶锚点归位率 ≥90%”，并同步更新 `BLACKTOP_CLUSTER` 为烘房后报交入口簇与打磨线，避免两套 S2b 规则在实现时产生代码残留或逻辑冲突。
4. **建议项 4：明确 W4.4a 中 `02_replay_eta.py`（W1 回放）的兼容逻辑**
   - **位置**：`docs/15` W4.4a（第 206 行）
   - **说明**：`02_replay_eta.py` 内部调用 `spike_w1/eta.py`。随着 `dim_loop_duration` 扩列为 4 元组，需确认 `spike_w1/eta.py` 中 `resolve` 函数（依赖 `row[-1]` 为样本量 n）及 `tables["loop_dur"]` 解构不受影响，建议在 W4.1c/W4.4a 中补充对 `spike_w1/eta.py` 的解包回归测试说明。
